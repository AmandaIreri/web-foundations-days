# SnapShare — Scaling Plan (Day 7 Assignment)

A photo-sharing app where users upload photos and scroll a feed of
photos from the people they follow. This document estimates the load at
10 million registered users, picks an architecture that can carry it,
explains each component, walks through the upload flow, and names the
trade-offs.

---

## 1. Assumptions

The estimate below starts from the facts given in the brief and rounds
liberally — the goal of a back-of-the-envelope estimate is to know
whether we need 1 server or 1,000, not to be exact.

- 10,000,000 registered users.
- 10% are active on any given day → **1,000,000 daily active users (DAU)**.
- Each active user uploads 1 photo per day → 1,000,000 uploads/day.
- Each active user views 50 feed pages per day → 50,000,000 feed views/day.
- An average photo is 2 MB.
- Each photo also produces a 50 KB thumbnail (generated by a worker).
- Useful rounding: 1 day ≈ 100,000 seconds (true value 86,400).
- Useful rounding: 1 KB = 1,000 B, 1 MB = 1,000 KB, 1 GB = 1,000 MB,
  1 TB = 1,000 GB.
- Peak hours carry roughly 5× the average traffic.

---

## 2. Estimates

### Uploads per second
- 1,000,000 uploads/day ÷ 100,000 seconds/day = **10 uploads/s average**.
- Peak (×5): **50 uploads/s**.

### Feed views per second
- 50,000,000 feed views/day ÷ 100,000 seconds/day = **500 feed views/s average**.
- Peak (×5): **2,500 feed views/s**.

### Photo storage per year
- Originals: 1,000,000 × 2 MB = 2,000,000 MB ≈ **2 TB/day**.
- Thumbnails: 1,000,000 × 50 KB = 50,000,000 KB = 50,000 MB ≈ **50 GB/day**.
- Combined: ≈ **2.05 TB/day**.
- Per year: 2.05 TB × 365 ≈ **750 TB/year** (about 0.75 PB/year).

| Metric              | Average      | Peak (5×)   |
|---------------------|--------------|-------------|
| Uploads/s            | 10           | 50          |
| Feed views/s         | 500          | 2,500       |
| Storage/day          | ~2.05 TB     | —           |
| Storage/year         | ~750 TB      | —           |

## 3. Read-heavy or write-heavy?

SnapShare is overwhelmingly **read-heavy**: at the average we serve
about 500 feed views per second against only 10 uploads per second — a
**50-to-1 ratio**, and at peak the ratio is the same (2,500 vs 50).

The practical consequence is that the design should throw most of its
scaling effort at the **read path**: a CDN for the photo files
themselves, an application cache (Redis) for assembled feed pages and
hot user metadata, and read replicas for the database. Writes
(uploads) are an order of magnitude lighter and only need to be fast
enough to feel responsive — the truly slow part of an upload
(generating the thumbnail) is pushed to a background queue. This is
the same shape as QuickNotes from the worked example in the Day 7
notes, only larger.

---

## 4. Why photos are not stored in the database

The database holds the *one true copy* of **structured** data: which
users exist, who follows whom, and photo metadata (id, owner, caption,
`created_at`, storage URL). The actual 2 MB image bytes do **not**
belong in the database for three reasons.

1. **Bloated rows slow every query.** A `SELECT id FROM photos WHERE
   user_id = 7` would have to wade past megabytes of binary data per
   row even though it never returns the bytes. Indexes help, but the
   table is still painful to scan, back up, or replicate.
2. **Databases are optimised for structured rows, not blobs.**
   Relational engines are tuned for tight, fixed-width columns and
   short lookups; streaming a 2 MB blob out of a row is slower per
   byte than reading it from a file system or object store, and the
   per-GB storage cost is higher.
3. **Photos must be served at scale from many locations.** A CDN's
   edge servers cannot pull bytes from a database row — they need an
   HTTP endpoint, which is what object storage provides natively.

Instead, the photo bytes go to **object storage** (Amazon S3, Google
Cloud Storage, Cloudflare R2), which is built for huge volumes of
binary files at low cost. The database stores only the **URL** pointing
at the file. Object storage also integrates naturally with a CDN: edge
servers pull images from the bucket and cache them close to users.

## 6. What each component solves

- **DNS** — translates `snapshare.com` into the IPs of the load balancer
  (for API calls) and the CDN (for static assets), so the browser knows
  where to connect.
- **CDN** — serves HTML/CSS/JS and the photo bytes from edge servers
  physically close to each user, cutting latency from hundreds of
  milliseconds to tens and absorbing the majority of read traffic
  before it ever reaches our origin.
- **Load balancer** — spreads API requests across the app servers and
  runs health checks so a crashed server is removed from rotation
  within seconds; it is what lets the app tier scale horizontally and
  removes the app server as a single point of failure.
- **App servers (×3, stateless)** — run the API code (auth, feed
  assembly, upload orchestration); because they keep no per-user state
  in memory, any of them can serve any request, which is exactly what
  the load balancer needs.
- **Redis cache** — stores assembled feed pages and hot user metadata in
  RAM so a feed view that would cost ~20 ms against the database
  returns in ~1 ms; this is where the read-heavy nature of SnapShare is
  absorbed.
- **Primary database** — the single source of truth that accepts all
  writes (new users, follows, photo metadata rows), enforcing the
  schema, foreign keys and uniqueness rules — the things Day 6 taught
  us belong in the database.
- **Read replica** — a copy of the primary that serves read-only
  queries, so the hundreds of feed-view SELECTs per second do not pile
  up on the primary and slow down uploads; if the primary dies, a
  replica can be promoted (failover).
- **S3 / object storage** — holds the 2 MB originals and 50 KB
  thumbnails cheaply and at essentially unlimited scale, and serves
  them to the CDN; the database stores only the URL, keeping rows
  small.
- **Message queue** — accepts the "make thumbnail" job from the app
  server the instant the upload finishes, so the user gets a `201
  Created` response immediately instead of waiting for image
  processing.
- **Thumbnail worker** — pulls jobs from the queue, resizes the photo
  to 50 KB, writes the thumbnail back to object storage, and updates
  the database row — keeping slow CPU work off the request path and
  smoothing bursts by processing jobs in order.

## 7. Upload flow, step by step

1. The user picks a photo in the browser and taps **Upload**. The
   browser asks DNS for `snapshare.com`, gets the load balancer IP, and
   sends `POST /photos` with the image bytes (over HTTPS).
2. The **load balancer** picks the least-busy healthy app server and
   forwards the request (least-connections strategy).
3. The **app server** checks the auth token to identify the user, then
   validates the upload (file type, size under the limit, caption
   length).
4. The app server streams the 2 MB image bytes directly to **object
   storage** (S3) — they never touch the database. S3 returns the
   object's URL.
5. The app server writes a single row to the **primary database**:
   `(photo_id, user_id, caption, original_url, thumbnail_url = NULL,
   created_at)`. The thumbnail URL is `NULL` because the thumbnail
   does not exist yet.
6. The app server pushes a job onto the **queue**:
   `{photo_id, original_url}`. The worker needs these to find the
   image and to know which row to update later.
7. The app server **invalidates the cache** for the uploader's feed
   (and the feeds of anyone who follows them) by deleting the relevant
   `feed:user:*` keys, so the next read fetches fresh data instead of
   serving stale feeds that omit the new photo.
8. The app server responds **201 Created** to the browser with the
   photo's metadata. The user sees their photo appear in their own
   feed immediately.
9. Within a few milliseconds the **thumbnail worker** picks the job
   off the queue, downloads the original from S3, generates the 50 KB
   thumbnail, uploads it back to S3, and runs
   `UPDATE photos SET thumbnail_url = ? WHERE id = ?` on the primary.
10. The primary replicates the new `thumbnail_url` to the **read
    replica** a few milliseconds later. From now on, anyone scrolling
    their feed is served the small thumbnail from the CDN, not the 2 MB
    original — saving bandwidth and load time for every viewer.

## 8. Trade-offs

### Trade-off 1 — Speed vs freshness (the caching trade-off)
Caching feed pages in Redis makes the average feed view ~1 ms instead
of ~20 ms, which is what makes 2,500 feed views per second at peak
survivable on a handful of app servers. The cost is **stale data**:
a user who just posted may see an old feed for the few hundred
milliseconds it takes for the cache key to be deleted and
re-populated. For a photo app this is acceptable — a one-second-stale
feed is not a crisis the way a one-second-stale bank balance would be
— so we choose speed over freshness.

### Trade-off 2 — Consistency vs availability (CAP at the database)
Using a primary + read replica means a feed view can read from the
replica while a brand-new upload is still being copied across. For a
few milliseconds after upload the replica does not yet have the new
row, so a read may return "no new photo" even though the user just
posted one. We accept this **eventual consistency** in exchange for
**high availability** under heavy read load — if we instead forced
every read to hit the primary, the primary would become the bottleneck
and the system would slow to a crawl at peak. The right call for
SnapShare because feeds do not need to be perfectly linearisable.

### Trade-off 3 — Simplicity vs scalability (monolith vs microservices)
SnapShare at 10 million users can still be a well-organised monolith on
the app tier (auth, feeds, uploads, search all in one codebase),
because the read-heavy load is absorbed by the cache and CDN, not by
smarter code. We resist the temptation to split into microservices
(a photos service, a feed service, a follow-graph service) until a
clear pain point appears, because each microservice adds
network-failure modes and operational complexity. The trade is a
**lower scalability ceiling** in exchange for **much simpler debugging
and deployment** — and that trade is right for SnapShare at this
stage.

---

## 9. Summary

SnapShare at 10 million users turns out to be a **read-heavy** system
serving ~500 feed views per second against only ~10 uploads per second,
with about **750 TB** of photo bytes accumulating per year. The design
puts the photos in object storage and serves them through a CDN,
absorbs feed reads in Redis, scales the app tier horizontally behind a
load balancer, replicates the database for read throughput, and defers
the slow thumbnail work to a queue + worker. Every one of those
decisions trades a little consistency or simplicity for a lot of
throughput — which is the right trade for a social photo feed.
